# RAG 评估说明

## 1. 评估目标

本项目将检索评估限定为两个可验证问题：

1. 与问题相关的政策证据能否进入前若干个检索结果；
2. 必要条款能否完整装入提供给生成模型的上下文。

这套评估不测量最终回答是否正确，因此不把检索指标表述为“问答准确率”或“业务可用率”。

## 2. 数据与划分

- 语料：8 份企业差旅样例文档，覆盖差标、报销、预订、应急和平台使用等主题；
- 开发集：16 道问题，用于实现检索链路和观察配置表现；
- 留出集：42 道问题，不参与配置选择，用于发现开发集过拟合；
- 无答案探测：4 道语料外问题，用于确认最近邻分数不能直接充当可靠拒答阈值。

题目和必要证据由项目内构造，不是独立业务专家标注，因此只能支持项目内工程决策。

## 3. 指标定义

| 指标 | 含义 | 用途 |
|---|---|---|
| Hit@K | 前 K 条中是否至少出现一条相关证据 | 检查基本召回能力 |
| Recall@K | 前 K 条覆盖了多少必要证据 | 检查多条款问题是否漏召回 |
| MRR@K | 第一条相关证据出现得有多靠前 | 检查排序质量 |
| 完整证据率 | 上下文是否包含问题所需的全部原文 | 检查切块与预算是否破坏条款 |

指标按固定来源和必要原文计算。证据被切碎后即使关键词出现，也不计为完整覆盖。

## 4. 基础检索对照

16 道开发题、Top-3 条件下的结果：

| 方案 | Hit@3 | 宏平均 Recall@3 | MRR@3 |
|---|---:|---:|---:|
| Dense | 100% | 86.46% | 0.8854 |
| BM25 | 87.50% | 83.33% | 0.8750 |
| Hybrid | 100% | 89.58% | 0.9375 |

Hybrid 在这组问题上提供了更好的证据覆盖和首条相关结果排序，但样本量较小，且问题来自同一批样例制度，不能据此声称它对所有企业知识库都更优。

## 5. 配置实验如何影响实现

参数实验的价值不是寻找一个可以对外宣传的“最优数字”，而是为实现选择提供证据并暴露边界。

| 决策点 | 观察 | 当前选择 |
|---|---|---|
| 切块方式 | 章节切块比固定窗口更容易保留完整条款 | 保留章节与自然段边界 |
| Top-K | Top-1 容易遗漏，多于 Top-3 会增加上下文 | 默认返回 Top-3 |
| 池化方式 | 当前 BGE 配置下 CLS 表现更稳定 | 明确使用 CLS，不依赖隐式默认值 |
| 检索模式 | Hybrid 在开发题覆盖更好，Dense 实现更简单 | Dense 默认，Hybrid 可选 |
| 证据预算 | 预算过小会截断必要条款，过大增加模型上下文 | 保留完整片段并设置上限 |
| 候选数量 | 更多候选没有表现出单调收益 | 不用扩大候选数替代检索质量 |

留出题的作用是检查这些选择换一批问题后是否仍然成立。部分开发集优势没有稳定延续，因此项目没有根据一次小型实验自动改写全部默认参数。

## 6. 工程验证

离线测试覆盖：

- 章节切块和稳定 ID；
- 证据去重与完整片段预算；
- BM25 排序与 RRF 融合；
- Milvus 重复 upsert 的幂等性；
- 开发集与留出集隔离；
- 来源约束和必要证据判定；
- 引用编号存在性及其能力边界。

运行命令：

```bash
pytest -q
```

真实模型与向量库评估：

```bash
python scripts/evaluate_rag_engineering.py
python scripts/evaluate_rag_parameters.py
```

原始协议、逐题结果和语料哈希保存在 `experiments/rag_engineering` 与 `experiments/rag_parameters`，便于复核结论来源。

## 7. 尚未证明的能力

- 没有使用真实企业内部制度或真实员工问题；
- 没有独立业务专家进行盲评；
- 没有评估最终生成答案的事实正确性；
- 没有形成经过验证的无答案阈值；
- 没有完成多模型横向比较、在线压力测试或成本评估；
- 引用编号正确不代表引用内容能够支持对应结论。

这些限制决定了当前结果适合说明检索工程方法，而不适合作为生产效果承诺。
